# WEB4 candidate delivery

Changes proceed through a committed branch, pull request, candidate qualification and explicit promotion. `scripts/qualify_release.py` fails on a dirty checkout or any failed gate. Output must be a new directory outside the checkout. The workflow pins third-party actions to commits, uv and build tools to versions, uses read-only GitHub permissions, cancels superseded builds and preserves evidence on failure.

Run `python scripts/qualify_release.py --output /tmp/qualification-UNIQUE` for the public candidate gates. It checks controlled documents, the frozen dependency lock, source tests, builds a wheel and tests that installed wheel in an isolated environment. Evidence includes the source commit, artifact SHA-256, dependency/license metadata inventory, individual command logs and evidence hashes. The inventory is not a vulnerability scan or legal license assessment. Build tool versions are pinned; byte-for-byte reproducible builds have not been established.

For owner-package qualification add `--runtime-root /workspace/braink-setup/web4-runtime`. This runs actual service and browser integration gates against the named runtime and makes test commits/restarts. Node 24 and Chromium must be installed. Use `--container-no-sandbox` only in the isolated cloud test container where Chromium sandbox support is unavailable; that result does not establish browser isolation. Private owner packages are restored through the authorized private repository; the public CI job does not receive them or pretend to run these additional gates.

Promotion requires review of the exact candidate and its evidence. Local tests do not establish independent assessment, public HTTPS readiness, hardware actuation or production approval. GitHub hosted Actions currently cannot start because the owner account has a billing lock. Local qualification remains executable. Branch-protection read access is denied to the integration, so enforcement is unknown; a PR alone does not establish enforced review. GitHub Projects creation is separately denied. Milestones, labels, issues and PRs remain usable.

The existing runtime retains its journals and signed namespace history across owned service restarts. This is the demonstrated recovery path. Do not replace mutable runtime state with a wheel or claim atomic rollback of a partially completed multi-register actuation. Preserve the source custody manifest, launch fingerprints, credentials and journals when evaluating a subsequent candidate. Deployment across failure domains and state migration require separately qualified work.
